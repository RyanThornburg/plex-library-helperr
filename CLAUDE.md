# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Uses [uv](https://github.com/astral-sh/uv) and Python 3.14+.

```bash
uv sync                                   # install deps (incl. dev group: pytest)
uv run main.py                            # run movers/profilers
uv run main.py --remove                   # run sonarr removers only
uv run main.py --empty-trash              # empty plex library trash only
uv run main.py --serve                    # web app (needs CF_ACCESS_* and ALLOWED_EMAILS env)
uv run pytest tests/ -v                   # all tests
uv run pytest tests/test_main.py::TestRunArr -v   # single test class
```

No linter/formatter is configured in `pyproject.toml`.

## What it does

A one-shot script that reads every movie (Radarr) / series (Sonarr), applies user-defined rules from `config/config.toml`, and issues bulk edits back to the *arr API. Three rule types:

- **Movers** — change root folder (with `move_files=True`) for media matching genre/tag/studio/network/certification filters; optionally tag moved items, then scan the old and new folders via Autoscan (or, without Autoscan, refresh the target Plex library).
- **Profilers** — assign a quality profile (and optionally set `monitored`) for media matched by title/studio/network.
- **Removers** (Sonarr only, `--remove`) — unmonitor then delete stale seasons/episode files from tagged series, keeping the latest `keep` seasons/episodes. Runs instead of movers/profilers, never uses `filter_time`.
- **Empty trash** (`--empty-trash`) — empties Plex library trash (the server has auto-empty off). Movers/removers only trigger scans, so this is scheduled separately, after scans finish.

`dry_run` should be assumed on when testing against a real library.

## Architecture

- `results.py` — `JobResult` (the `Change`s a job made, `scan_dirs`/`plex_libraries` left to scan, `errors` that stopped part of the job, and for removers the `removals` planned: a `PlannedRemoval` per series with its file ids/paths, which the UI approves) is passed into `run_arr`, `run_removers` and `empty_plex_trash` and filled as they go, so changes made before an exception are kept. A `Change` is one bulk edit / series removal / library trash / scan with a status: `done`, `dry_run`, `blocked` (a safety check such as `max_deletes`, `max_items` or a scan in progress) or `failed`. Results carry what the future API/UI acts on; why media was skipped stays in the log. Never put URLs or secrets in a `Change`, results will be stored and shown in the UI.
- `main.py` — all rule-matching logic, `run_job(job, settings) -> JobResult` (jobs: `movers` = movers and profilers, `removers`, `empty_trash`), which the API will call, and `main()`, which parses args, runs one job and logs its summary. Run as a script it exits 1 when the result has errors or failed changes. Radarr and Sonarr share one code path via the `arr_dispatch` table, which maps each to its arrapi class and method names (`all_movies`/`all_series`, `edit_multiple_movies`/`edit_multiple_series`) called through `getattr`. Per-instance work lives in `run_arr()`; `run_job()` catches `ArrException` per instance so one failure doesn't stop the other. When adding *arr-specific behavior, branch on `log_name` ("RADARR"/"SONARR") or extend that tuple rather than duplicating the loop.
- Matching functions (`get_matches_based_on_mover_rules`, `get_media_matching_profile_rules`) are pure: they take media lists and return the matching `Movie`/`Series` objects, which are passed directly to `edit_multiple_*`; all API side effects stay in `run_arr()`. Tests exercise these functions with `MagicMock` media objects (see helpers at the top of `tests/test_main.py`).
- Mover evaluation order: skip media already under `path` or any `exclude_paths` → apply excludes (tags, genres, certifications) → require each configured filter (studio, network, certification, genre with `genre_match`, tag with `tag_match`). All comparisons are `casefold()`ed. Movers run in config order and media matched by an earlier mover is skipped by later ones (first match wins).
- `config/__init__.py` — `load_config()` parses TOML into dataclasses in `config/models.py`. Remover durations (`min_age`, `skip_if_watched_within`) are parsed strictly and raise on a bad value, unlike `filter_time`, so a typo can never mean "delete now". If `config/config.toml` is missing it is copied from `config.toml.example`. `[settings].dry_run` is the default for each *arr section, which may override it with its own `dry_run`. `filter_time` (`7d`/`12h`/`30m`) becomes a `timedelta`; media is filtered by `added` against naive UTC now.
- `config/models.py` — dataclasses validate in `__post_init__` (movers/profilers need at least one matching criterion; `*_match` must be `any`/`all`). `_validate_rules` in `config/__init__.py` rejects `networks` on Radarr and `studios` on Sonarr rules. Custom `__repr__`s omit empty fields and mask `apikey`/`token` because the full config is logged at startup — keep secrets masked when adding fields.
- `remover.py` — `run_removers()` plans every series first, then acts. arrapi has no episode endpoints, so `SonarrEpisodes` calls `/api/v3` directly with `requests` (episodes, episodefile, queue/details, `PUT episode/monitor`, `DELETE episodefile/bulk`). `plan_series_removal()` is pure and is where the rules live:
  - Candidates are everything outside the keep window. Only numbered seasons/episodes **with files** count toward `keep`; specials (season 0) never count and are only removable with `include_specials`.
  - `seasons` mode is all or nothing: a season is removed only if every file's `episodeFile.dateAdded` is older than `min_age`. `episodes` mode works per file; a multi-episode file holding any kept episode is kept.
  - Watch protection (`skip_if_watched_within`) only counts recent plays of removal *candidates* (watching the latest episodes never blocks) and protects from the earliest watched candidate onward. It runs before the age filter, so watching a new season still protects older seasons after it. A watched special protects only specials.
  - Series-level skips: `series.added` newer than `min_age`, anything in the download queue, or invalid/missing Sonarr data (`InvalidSeriesData`). Bad data is logged and skipped, never guessed at.
  - A series tagged for two removers is logged as an error and skipped; a tag shared between removers is rejected at config load.
  - `remover_settings.dry_run` defaults to `true` independently of the global `dry_run`. `max_deletes` is all-or-nothing for the files a run deletes (removals only planned for review don't count). Episodes are unmonitored before files are deleted; if unmonitoring fails the delete is skipped.
  - A `RemovalPlan` holds `Unit`s (a season, or an episode file); `labels`/`file_ids`/`episode_ids`/`dirs` derive from them. Every plan is recorded in `result.removals`.
  - Applying a reviewed plan is `run_removers(..., approved={series_id: {file_ids}})`: only those series are planned again from fresh data (same skips), `RemovalPlan.restricted_to()` keeps only units whose every file was approved (so a season with a replaced file is kept whole, and newly eligible units aren't removed), and whatever isn't removed is reported as a `blocked` change. `remover_settings.dry_run` is ignored in this mode, `max_deletes` isn't.
  - Auto-approve: `run_removers(..., auto_approve=frozenset(rule keys))` deletes those rules' removals even with `remover_settings.dry_run` on, the rest are planned for review. `RemoverRule.key` (tags casefolded, sorted, comma joined; removers can't share tags) identifies a rule outside config.toml.
- `watch_history.py` — `WatchEvent`s (naive UTC) from Tautulli `get_history` (includes partial plays and all users, show TVDB id from `get_metadata` guids), falling back to Plex server history (completed plays only). Returns `None` on failure, and removers with `skip_if_watched_within` are then skipped. Events are matched to series by TVDB id, and by title only when the history has no TVDB id. Tautulli's `apikey` is a query param, so `requests` error text contains it: redact it before logging or storing any Tautulli error.
- `autoscan.py` — POSTs the old and new folders of moved media to Autoscan's `/triggers/manual`. Paths are sent as the *arr sees them; the rewrite on Autoscan's Plex target maps them to Plex paths and its `minimum-age` covers the async move.
- `plex.py` — fallback when Autoscan isn't configured: connects via plexapi and refreshes each library section collected from executed (non-dry-run) movers. Also `empty_plex_trash()` for `--empty-trash`: counts each movie/show section's trash via `/library/sections/{key}/all?type=<movie|episode>&trash=1` (includes old versions left by upgrades) and skips a section that is `refreshing` or over `[plex.empty_trash].max_items`, which guards against a missing mount trashing a whole library. Only then `list_trash()` fetches the items: Plex marks each trashed version (`Media`) with `deletedAt`, so an item with a live version is an upgrade leftover (only counted) and one without is fully deleted (`TrashedItem` in `result.trash`, listed on the run page). Fully deleted items are matched to the web app's removers by file name (`removed_files`, from `JobRunner.removed_files()`; sonarr and plex paths differ), and only unmatched ones count toward `max_deleted_items`. Its `dry_run` defaults to `[settings].dry_run`.
- `web/` — FastAPI app run by `main.py --serve` (one uvicorn worker on purpose: the scheduler will live in-process, no Redis). `create_app(settings, keys)` is a factory; tests pass `keys` to replace the team's signing keys.
  - `settings.py` reads `CF_ACCESS_TEAM_DOMAIN`, `CF_ACCESS_AUD` and `ALLOWED_EMAILS` and refuses to start if any is missing or malformed, so auth can never be half configured. Optional `REMOVERS_ALLOW_APPLY` (`true`/`false`, default off) must be one of those when set.
  - `auth.py` is pure ASGI middleware that wraps every route (static files and 404s too) except `PUBLIC_PATHS` (`/healthz`). It verifies `Cf-Access-Jwt-Assertion` (RS256 only, keys from `https://<team>/cdn-cgi/access/certs`, issuer, audience, exp), then the email against `ALLOWED_EMAILS`. Denial reasons are logged, never returned. Fails closed, including when Cloudflare's keys can't be fetched.
  - `security.py` adds a strict CSP (no inline scripts/styles, no third-party content, so self-host any JS such as htmx) and other headers, and rejects non-GET requests whose `Origin` doesn't match `Host` (CSRF). It runs before auth.
  - `jobs.py` — `JobRunner`: one worker thread runs queued `JobRun`s in order, so jobs never overlap (no locks needed). `submit()` refuses a job that is already queued/running (`AlreadyActive`). Each run calls `config.load_config()` fresh and then `main.run_job()`, with `config.force_dry_run()` when the run asked for dry run. Dry run can only be forced on: a non-dry run uses config.toml's settings, so the UI can never make a dry config live. The one exception is `submit_apply()`, applying a reviewed removers plan (`JobRun.plan_run_id`, `approved`), which runs live past `remover_settings.dry_run`. It needs `REMOVERS_ALLOW_APPLY=true` (`WebSettings.allow_remover_apply`, an env var so the UI can never turn it on, checked again when the run executes), a finished non-apply removers run whose `approvable()` removals (`dry_run`/`blocked`) include every selected series, the plan under `PLAN_MAX_AGE` (7 days), and no earlier apply of that plan. `apply_problem()` says why not; pages show it. Auto-approve is the other: `RemoverRuleSetting` rows (`remover_rule_settings`, keyed by `RemoverRule.key`) set on the Removers page; `auto_approved_rules()` returns their keys only when `allow_apply`, and `_execute` passes them as `auto_approve` only for a removers run that isn't forced dry and isn't applying a plan, so forced dry runs never delete. `routes.config_modes()` reports removers as partly live (None) when auto-approved rules would delete, so the job card, Run… confirmation and schedule form say so. `RunLogCapture` stores that run's log lines, filtered to the worker thread so request logs don't leak in. At startup, runs left queued/running are marked failed and never resumed (removers delete files). `wait_idle()` is for tests.
  - `scheduler.py` — `Scheduler` thread wakes a second into every minute and `tick(now)`s: each enabled `Schedule` whose cron has matched since `max(last_fired_at, updated_at, started_at)` is submitted to the `JobRunner` (trigger `schedule`, `JobRun.schedule_id` set). So missed times fire at most once, never for times before the app started or the schedule was last edited (an edit resets it). `last_fired_at` is written before submitting; an `AlreadyActive` job skips that time. Tests pass `run_scheduler=False` to `create_app` and call `tick()` directly. Schedules are stored only in the database, not config.toml: the plan is to move config into the UI over time.
  - The scheduler also queues a follow-up empty trash (trigger `followup`) via `trash_followup_due()`, worked out from run history only: `TRASH_FOLLOWUP_DELAY` after the last live movers/removers run with a `done` move/remove since the last `emptied()` run (config settings, nothing blocked/failed; a forced dry run doesn't count, a config-dry one does), retried up to `TRASH_FOLLOWUP_ATTEMPTS`, looking back `TRASH_FOLLOWUP_LOOKBACK`.
  - `cron.py` — own 5-field parser (no dependency): numbers, `*`, ranges, steps, lists, `@hourly` etc. Each `Schedule` has an IANA `timezone` (`parse_zone()`, `tzdata` is a dependency so the image's zoneinfo doesn't matter) and `next_after_utc(after, zone)` matches the cron's wall time there, converting from/to naive UTC; the container's TZ is never used. Day and weekday are OR'ed when both are restricted, like cron. `parse()` raises ValueError naming the bad field, and rejects expressions that never run.
  - `config.force_dry_run()` must turn on every `dry_run` in the settings; `tests/test_jobs.py` walks the settings tree to catch a new one being missed. `config.config_dry_run(job, settings)` says whether a job as configured is dry (None = mixed between arrs).
  - `routes.py` — pages: `/` (job cards with the config's dry run state, recent runs), `GET /jobs/{job}/confirm` (every non-forced run goes through this page, which says whether it's live; there's no JS `confirm()` under the CSP), `POST /jobs/{job}?dry_run=` (query param), `/runs/{id}` (refreshes with `<meta refresh>` while active; a removers run lists its `removals` with checkboxes when approvable, and leaves those out of its changes table), `GET /runs/{id}/apply?series=` (confirmation with the file total and `max_deletes`) and `POST /runs/{id}/apply?series=` (query params again), `/schedules` (list, pause/resume), `/schedules/new` (its time zone select is set to the browser's zone by `static/app.js`) and `/schedules/{id}` (form; POSTs go to `/schedules`, `/schedules/{id}`, `/schedules/{id}/toggle`, `/schedules/{id}/delete`). Form bodies are parsed by `form_fields()` with `parse_qs`, capped at `MAX_FORM_BYTES`, so no python-multipart; unchecked checkboxes are absent. JSON API: `POST /api/jobs/{job}` (`{"dry_run": true}` by default, 409 when active), `GET /api/runs`, `GET /api/runs/{id}`, `GET/POST /api/schedules`, `GET/PUT/DELETE /api/schedules/{id}` (422 with `errors` when invalid), `POST /api/runs/{id}/apply` (`{"series_ids": [...]}`, 422 with `error` when refused), `/removers` (config's remover rules with an auto-approve switch; turning on goes through `GET /removers/auto-approve?rule=`, then `POST /removers/auto-approve?rule=&enabled=`), `GET /api/removers`, `POST /api/removers/auto-approve` (`{"rule", "enabled"}`; turning on needs the rule in config.toml, turning off doesn't). New schedules default to dry run in both the form and the API. Schedules are validated by `scheduler.schedule_errors()`. `requested_by` is the Access email. Templates read results as dicts: use `change["items"]`, since `change.items` is the dict method.
  - Tests call `create_app(settings, keys, run_job, load_config)` with fakes for all three, so no test reads a real config.toml or calls an arr.
  - The web app logs to `logs/web.log` (`logging_config("web.log")`), separate from the CLI's `log.log`, since they run in different containers and two processes rotating one file lose lines.
  - `db.py` uses SQLite at `$DATA_DIR/helperr.db` (WAL, foreign keys, busy timeout). Schema changes go through Alembic migrations in `web/migrations/versions`, applied at startup. Generate new ones with autogenerate against a scratch db, then tidy them.
  - The `localtime` filter renders `<time datetime="...Z">... UTC</time>`, which `static/app.js` rewrites in the browser's time zone; there's no server-side time zone.
  - Templates link assets root-relative (`/static/...`). Never use `url_for` for URLs: behind cloudflared the app sees `http`, so absolute URLs would be mixed content.
  - No interactive API docs (`/docs`, `/openapi.json`); they would be one more surface to protect.
- `logging_config.py` — dictConfig with a Rich console handler (`markup=False`, so titles with brackets render literally) and a rotating plain-text file at `logs/log.log`. Log lines are prefixed with `log_name` and a tab.

## Notes

- Code uses Python 3.14 syntax, e.g. unparenthesized multi-exception `except A, B:` in `plex.py` (PEP 758) — this is intentional, not a bug.
- `main()` takes `argv` (tests call `main.main([])` so pytest's argv isn't parsed).
- `config/config.toml` holds real credentials and is gitignored; edit `config.toml.example` for documented defaults and keep the README config tables in sync when adding rule fields.
- `DATA_DIR` (set to `/config` in the Dockerfile) moves `config.toml` and `logs/` out of the code dirs; unset, they stay at `config/config.toml` and `logs/`. Docker can't mount over `/app/config` because that's the config Python package.
- `.github/workflows/docker.yml` runs the tests, then builds the image; pushes to `mainline` publish `ghcr.io/ryanthornburg/plex-library-helperr` (`latest` and `sha-<commit>`), which Unraid pulls. Actions are pinned to commit SHAs (with the version in a comment) and Dependabot updates them along with uv and the base images.
- `.dockerignore` is an allowlist so `config/config.toml` never reaches the build context. When adding a module outside the top level or `config/`, add it there and to the Dockerfile's `COPY` lines.
